1. Executive Summary

During a systematic quality assurance and security investigation of the AI-assisted ("vibe-coded") RealWorld (Conduit) web platform, the QA team evaluated all core user workflows: user sign-up, session authentication, content authoring, inline editing, article deletion, logout, input validation, and boundary conditions.

The evaluation uncovered six reproducible defects ranging from infrastructure abandonment to critical authentication bypass and data integrity flaws. Most alarmingly, the official production endpoints documented across the repository suffer from catastrophic hosting failures (404 NoSuchBucket on AWS S3 and 530 Cloudflare DNS), while the active backend platform allows duplicate user registration requests to silently overwrite or issue authentication tokens without verifying credentials.

4. In-Depth Root-Cause Analysis (RCA)

Investigation Target: Issue #1 — Silent Duplicate Registration & Unauthenticated Token Generation
Classification: Critical Security Vulnerability / Account Takeover (ATO) Vector · CWE-287 / CWE-362

4.1 Incident Description (What is Happening?)

When a user registration request (POST /api/users) is submitted with an email address or username already registered in the system, the application fails to reject the transaction with an HTTP 422 Unprocessable Entity response. Instead, the backend returns an HTTP 201 Created status code and issues a fully authenticated JSON Web Token (JWT) linked to the existing user's identity. This allows any unauthenticated actor who knows a target user's email address to immediately hijack their session and obtain full read/write privileges over their profile and content without entering the user's password.

4.2 Root-Cause Identification (Why is it Happening?)

Investigation reveals two compounding architectural defects within the AI-generated persistence and controller layers:

First, the database migration scripts failed to declare UNIQUE constraints on the users.email and users.username columns. Consequently, the persistence layer cannot enforce record uniqueness at the relational engine level. Second, the controller logic was generated using an unsafe ORM shorthand method—specifically User.findOrCreate() or User.upsert()—without a preceding uniqueness verification check. Because findOrCreate() locates the existing record when a collision occurs rather than throwing an exception, execution seamlessly flows into the token generation utility, signing and returning a valid JWT for the matched user.

4.3 Comprehensive Remediation Plan (How to Fix It)

The defect must be addressed across all three architectural tiers: database constraints, schema validation middleware, and controller logic.

Step 1: Database Migration (Relational Constraint Integrity)

-- Migration: Add case-insensitive unique indexes on email and username ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email); ALTER TABLE users ADD CONSTRAINT uq_users_username UNIQUE (username); CREATE UNIQUE INDEX idx_users_email_lower ON users (LOWER(email));

Step 2: Input Validation Layer (Zod / Joi Schema)

import { z } from 'zod'; export const RegisterUserSchema = z.object({ user: z.object({ username: z.string().min(3).max(30).regex(/^[a-zA-Z0-9_-]+$/), email: z.string().email("Invalid email format"), password: z.string().min(8, "Password must be at least 8 characters long"), }), });

5. Strategic Engineering Recommendations

  • Mandate Automated Synthetic Probing: Configure an automated workflow (such as PulseQA n8n Uptime Monitor) to ping critical API routes every 5 minutes and immediately page engineers when Cloudflare 530 or S3 404 faults occur.
  • Implement Architectural Linting for AI Code: Add pre-commit static analysis rules that flag ORM calls such as upsert() or findOrCreate() on sensitive authentication endpoints.
  • Migrate to Secure Cookie Tokens: Cease storing JWT credentials in browser localStorage; migrate to HttpOnly, Secure, SameSite=Strict session cookies to nullify XSS token exfiltration attacks.
